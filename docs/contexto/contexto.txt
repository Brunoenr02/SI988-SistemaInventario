a que te refieres con contrato de api

Buena pregunta, es un término que puede sonar confuso si no se ha visto antes.

Un "contrato de API" es el documento donde se define, ANTES de programar, cómo va a "hablar" el frontend (la app Flutter) con el backend (la API que conecta con MSSQL y NoSQL). Es básicamente un acuerdo por escrito de:

Qué endpoints (URLs) va a tener la API. Ejemplo: POST /medicamentos, GET /stock, POST /transferencias.
Qué datos hay que enviarle a cada uno (el "request"). Ejemplo, para POST /medicamentos:
json
{
  "gtin": "7501234567890",
  "nombreComercial": "Paracetamol 500mg",
  "lote": "L2026A",
  "fechaVencimiento": "2027-05-01"
}
Qué te va a devolver cada uno (el "response"). Ejemplo:
json
{
  "id": "med_001",
  "estado": "registrado",
  "mensaje": "Medicamento ingresado correctamente"
}
Qué errores puede devolver y con qué código (ej. 400 si falta un campo, 401 si no está autenticado, 404 si no existe el lote).
Por qué es importante hacerlo ANTES de programar
Es la razón por la que Bruno (backend/BD) y Walter/quien haga el frontend pueden trabajar en paralelo sin bloquearse: si ya está definido que el login (POST /auth/login) va a recibir {usuario, contraseña} y devolver {token, rol}, entonces:

David/Walter pueden construir la pantalla de Login usando ese formato como referencia, aunque el backend real todavía no exista (usan datos "simulados" con ese mismo formato).
Bruno construye el backend real sabiendo exactamente qué se espera que reciba y devuelva.
Cuando ambos terminan, se conectan sin sorpresas porque respetaron el mismo "contrato".

En qué formato se hace normalmente
No hace falta algo muy elaborado para un proyecto académico. Puede ser:

Un archivo Markdown simple en /docs/api-contract.md con la lista de endpoints (como el ejemplo de arriba).
O, más formal, un archivo OpenAPI/Swagger (un estándar para documentar APIs) — pero para tu nivel de proyecto, el Markdown simple es suficiente y más rápido de sustentar.
